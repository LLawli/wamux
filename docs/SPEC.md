# wamux: Technical Spec

How the daemon is built. The contract itself lives in
[`crates/wamux-proto/proto/`](../crates/wamux-proto/proto/) and the schema in
[`crates/wamux/migrations/`](../crates/wamux/migrations/) and
[`crates/wamux/migrations_sqlite/`](../crates/wamux/migrations_sqlite/); this
document explains the mechanisms around them and does not restate either.

## Layout
A Cargo workspace. Each module directory opens with a doc comment that says what
it holds; read that rather than a file list here.
```
crates/
  wamux-proto/         # the gRPC contract, generated by build.rs (tonic-prost-build,
                       #   vendored protoc) whenever proto/ changes
    proto/             # package wamux.v1: the socket contract, source of truth;
                       #   FILE_DESCRIPTOR_SET (reflection) covers this package only
    proto/store/       # package wamux.store: the on-disk blob format, no services,
                       #   not part of the socket contract
  wamux-types/         # named domain types (JIDs, MediaKind, closed enums) and
                       #   WamuxError with its tonic::Status mapping
  wamux/               # the daemon (lib + `wamux` bin)
    migrations/        # Postgres schema  } same number and name per change from 0005
    migrations_sqlite/ # SQLite schema    } on; one older offset (CLAUDE.md, Migrations)
    src/
      main.rs          # entry point. No arguments serves: load config, refuse if
                       #   another daemon serves the socket, prepare the spool,
                       #   open the store (migrations run here), load accounts (no
                       #   connect: the edge connects), bind, serve, graceful
                       #   shutdown. `wamux store ...` are one-shot operator commands
      cli.rs           # the command line: serve, `store decrypt`, `store rotate-key`
      server.rs        # assemble the tonic server: every service, the
                       #   request-observability and peer-allowlist layers,
                       #   optional reflection
      observe.rs       # the per-request tower layer (one log line + metrics) and
                       #   the Prometheus recorder
      error.rs         # building a WamuxError from a whatsapp-rust error
      config.rs        # Config (figment: TOML + WAMUX_ env)
      services/        # one gRPC service impl per file, thin handlers
      domain/          # transport-agnostic logic the handlers call, one module
                       #   per concern, unit-tested
      state/           # per-account runtime: registry, handles, replay ring,
                       #   event bridge, send echo
      storage/         # StorageEngine and its engine families (see Storage)
      transport/       # the Unix socket, the peer allowlist, signal-driven shutdown
      spool/           # the on-disk media spool (see Media)
      stress/          # mock WhatsApp server, CDN and peer, for the service suites
                       #   and scale tests (`stress` feature only)
    tests/             # integration tests (see Verification)
  wamux-tools/         # development binaries (src/bin/), never shipped
docs/crate-notes/      # verbatim whatsapp-rust/wacore API extraction (reference)
```

## gRPC services (package `wamux.v1`)
One line per service on what it covers; the RPCs and messages are in
`crates/wamux-proto/proto/`. Only the mechanisms the proto does not make obvious
are noted here.
- **AccountService**: account lifecycle (create, list, status, pair by QR or
  code, connect, disconnect, logout, delete). `Connect`/`Disconnect` are named
  `ConnectAccount`/`DisconnectAccount` to avoid colliding with tonic's generated
  client `connect`. Connecting or pairing takes `backfill_history` (see
  Multi-account runtime).
- **EventService**: `SubscribeEvents` (server stream). Selector = account | all |
  none; `replay_from_ring` for ring replay. `EventEnvelope` is a oneof over every
  event the core relays; the cases are in `events.proto`.
- **MessagingService**: sends (text, media, reactions, edits, deletes, contacts,
  interactive replies, polls), history fetch, presence, read state, chat actions,
  poll votes and status posts. `SendMedia` and `PostStatusMedia` are client
  streams. Notes:
  - Read state is one WhatsApp operation per RPC and the edge composes: `MarkRead`
    sends the RECEIPT that turns the other person's ticks blue; `MarkChatRead` and
    `MarkUnread` are app-state mutations that only reach this account's own
    devices (issue #20, [breaking changes](BREAKING-CHANGES-2026-09-02.md)).
  - `AggregatePollVotes` sends no stanza: it opens the votes the edge supplies
    (issue #13).
  - `RevokeStatus` needs the edge to hand back the recipients it posted to
    (issue #41).
  - `GetStatusAudience` reads the audience the library last synced from the
    phone, the same `StatusPrivacySetting` an `AccountSettingUpdate` event
    carries (issue #89). An unset `audience` is "not synced yet", never "all
    contacts", and the audience chooses no recipients: a status goes to the
    `recipients` the edge posts it to.
- **MediaService**: `DownloadMedia` (server stream: meta frame + byte chunks).
- **GroupService**, **NewsletterService**: group and channel operations. The group
  settings an admin sets by mode (`SetGroupMemberAddMode`, `SetGroupMemberLinkMode`,
  `SetGroupMemberShareHistoryMode`) take the enum `GetGroupMetadata` reports;
  UNSPECIFIED and UNKNOWN are `InvalidArgument`. The link and history modes go out
  as a MEX mutation, the other settings as `w:g2` IQs.
- **ContactService**: lookups, profile, push name, about text, presence subscription,
  identity, blocklist. `BlockContact` needs the LID<->PN pair the client already
  learned (`FailedPrecondition` without it); the core never resolves it itself.
  `GetPushName` takes an `AccountRef`: it is the account's OWN name, the getter
  that pairs with `SetPushName`.
- **AdminService**: Prometheus metrics and the daemon's liveness/readiness check
  (see Notable constraints).
- **Identity (LID<->PN)**: `InboundMessage.sender_alt`/`recipient_alt` relay the
  stanza's other-namespace jids verbatim; `ContactService.ResolveLidPn` (batch,
  live client, cache-aside) and `ContactService.ListLidMappings` (storage-side,
  works disconnected) read the mapping the library keeps. The core only reports
  pairs the client already learned: no lookup policy, no guessing (issue #1).

## Multi-account runtime (`state/`)
- `AccountRegistry` is the shared state every service is built with (an `Arc`).
  MessagingService and MediaService also get the `MediaSpool` and `media_max_bytes`,
  EventService the shutdown signal, and AdminService the Prometheus handle. It owns the
  storage engine (`Arc<dyn StorageEngine>`, whichever engine the DSN selected),
  `DashMap<Uuid, Arc<AccountHandle>>`, and an `external_ref` index.
- On startup the registry loads every stored account as a handle and connects
  none of them. Connecting is the edge's call.
- `AccountHandle` holds: `device_id`, the live `Arc<Client>`, the **supervisor**
  task that owns the spawned bot's `BotHandle`, a `broadcast` event channel
  (capacity from `Config::broadcast_capacity`), the `EventRing`, and a
  `watch<ConnectionState>`.
- `bot_factory::build_bot` wires the engine's per-account `Backend` + tokio
  transport/runtime + the library's HTTP client (media CDN) + the `event_bridge` `on_event`
  closure, and sets the Noise certificate policy. History sync is skipped by
  default (relay-pure) unless the request sets `backfill_history`; then history
  flows as `HistorySyncEvent`.
- `event_bridge::dispatch` updates state, maps the event (`domain::event_mapping`;
  one library event can become several envelopes, each with its own seq), stamps
  seq+timestamp, pushes to the ring **only if `replayable`** (history-sync blobs and
  events over `replay_max_event_bytes` are excluded: bulk, not live replay, so they
  don't pin memory per account), then broadcasts. Ring first is what lets an
  all-accounts subscriber recover the events a new account emitted before its
  forwarder attached.
- Send echo (issue #22): WhatsApp echoes a message to every device on the account
  except the sender, and the relay is one device shared by every consumer, so the
  relay publishes an `InboundMessage` (`key.from_me` true) for each message sent
  through `MessagingService`, to every subscriber including the caller (consumers
  dedupe on the message id; a send whose id came back empty gets no echo). It is
  the one message on the bus that WhatsApp did not produce (the `gap` and
  `subscription_gap` markers below are the core's other synthetic events).
- `connect` is idempotent and **edge-driven** (the core keeps no per-account
  connection policy and reconnects nothing at startup). It honours a soft
  connection budget (`max_connected_accounts`; `ResourceExhausted` past it) and
  spawns a supervisor that awaits the run loop's **terminal** exit. The library
  owns transient reconnection (Fibonacci backoff); the supervisor only fires when
  it has given up, then marks the account down truthfully (so `is_running` never
  lies) and releases the budget slot. Any reconnect-after-terminal is edge policy.
- `stop`/`disconnect` are **graceful**: `Client::disconnect` (flush + close) then
  await the supervisor within `graceful_stop_timeout_ms`, detaching on timeout.
- `EventService` single-account → one forwarder; all → one per handle into the
  stream's shared mpsc, plus a follower that attaches a forwarder (full-ring
  replay) for each account created later (a `subscription_gap` marker if it misses
  creations). Delivery is **lossy under lag**: a slow subscriber gets a `raw` "gap"
  marker (carrying the current state) and resyncs via `GetAccountStatus`
  (authoritative watch). Each forwarder lags on its own broadcast receiver, so one
  slow subscription never stalls another (no cross-account head-of-line blocking);
  within one all-accounts stream, the shared queue is that client's backpressure.

## Storage (`storage/`)
- One `StorageEngine` is the only plug point. The `database_url` scheme picks the
  engine, so a config can never name one engine and point at another's database:
  `postgres://` or `postgresql://`, `sqlite://`, and `turso://` (experimental,
  only in a binary built with the `turso` cargo feature). Anything else fails at
  startup.
- Two families implement wacore's store traits on a device-scoped backend type
  (`Backend` is the traits' blanket impl): `sql/` (Postgres and SQLite through
  sqlx) and `turso/` (the turso crate). Runtime queries, no compile-time DB. The
  statement text is written once, in `storage/statements/`, and both families run
  it. Turso runs the SQLite migration set.
- One database. `accounts` is the parent: it maps the public UUID and
  `external_ref` to an integer `device_id` (generated by the engine; SQLite's
  `AUTOINCREMENT` never hands a deleted account's id to a new one). Every
  per-account row is scoped by that `device_id` and hangs off
  `accounts(device_id)` `ON DELETE CASCADE`, so `DeleteAccount` is one delete.
  Store-wide markers (blob format, encryption state) are single-row tables.
- Connection shape is per engine: Postgres a pool (`db_max_connections`); SQLite
  one writer behind the group commit plus a read-only pool (#173); Turso one
  connection behind the group commit mutex.
- **Byte formats** (`storage/blob_codec.rs`, identical across engines): raw bytes
  for keys/sessions/records, serde_json for `device_registry`, and protobuf
  (`crates/wamux-proto/proto/store/blobs.proto`, #31) for the three structured
  blobs: the whole `Device` (runtime-only `device_props` restored from
  `DEVICE_PROPS` on load), app-state versions and app-state sync keys. The last
  two keep the field numbers of whatsapp-rust's own sqlite backend. Field-tagged,
  so a field upstream adds decodes as its default instead of making every stored
  blob unreadable, as bincode did. `blob_format` records the format; a store
  still on bincode is converted on open (`storage/bincode_upgrade.rs`) by 0.2.x,
  the last release line that does; 0.3.0 refuses one (#84, #179).
- **Encryption at rest** (#164): with `store_key_file` set, the secret columns are
  sealed (XChaCha20-Poly1305, bound to device, table, column and row) on top of
  the formats above; see `storage/blob_cipher.rs` and
  [DEPLOYMENT.md](DEPLOYMENT.md#encryption-at-rest). The `wamux store` CLI
  decrypts a store or rotates its key with the daemon stopped.

## Media
- Send: `MediaService` is not used for send. `MessagingService.SendMedia`
  client-streams a header then the bytes inline (the core never fetches a URL);
  the bytes are encrypted into the media spool on disk and uploaded with
  `Client::upload_stream`, then the matching `wa::Message` is built.
- Receive: inbound events carry a `MediaDescriptor`; the edge later calls
  `DownloadMedia`, which decrypts into the media spool
  (`download_from_params_to_writer`), then streams a meta frame and byte chunks.
- The spool (#79) keeps memory per transfer constant: spool files are unlinked
  from creation, `media_max_bytes` bounds one transfer, and
  `media_spool_max_bytes` bounds all transfers in flight (`ResourceExhausted`
  past it). See [DEPLOYMENT.md](DEPLOYMENT.md#the-media-spool-79).
- Sticker packs (#58, receive-only): the event's `media` is the pack's ZIP under
  `MEDIA_TYPE_STICKER_PACK`, and `sticker_pack.thumbnail` is a second descriptor
  under `MEDIA_TYPE_STICKER_PACK_THUMBNAIL`, with the same media key. Both are
  download-only `MediaKind`s: `MediaKind::parse_sendable` refuses them,
  `parse_downloadable` accepts them.

## Transport and config
- Unix socket only, no TCP, no TLS. The socket gets `socket_mode` (default 0660)
  and, if `socket_group` is set, that group (chowned in a private staging
  directory before it appears at the path, #77); otherwise the daemon's process
  group, so run wamux as the group that should share the socket. Startup refuses to run when another daemon already serves the path.
  `allowed_uids`/`allowed_gids` add an optional `SO_PEERCRED` allowlist. See
  [DEPLOYMENT.md](DEPLOYMENT.md).
- SIGTERM/SIGINT fire one shutdown that ends every event stream; the server then
  drains within `shutdown_grace_ms`, the accounts stop gracefully, and the socket
  is unlinked (#35).
- `Config` is loaded once at startup: defaults, then the TOML file (`WAMUX_CONFIG`
  or `wamux.toml`), then `WAMUX_` env (env wins). Each field's doc comment in
  `config.rs` is the reference. `store_key_file` names a path; the key itself is
  never read from the environment.

## Notable constraints / gotchas
- One prost only: tonic codegen uses **prost 0.14** through `tonic-prost-build` (#61).
  waproto dropped prost for `buffa` in whatsapp-rust 0.7, so a `wa::Message` encodes
  through `whatsapp_rust::buffa::Message`, not a second prost.
- Some library queries (`is_on_whatsapp`, `get_user_info`, participating groups)
  return **non-Send** futures (HRTB). They are driven on a blocking thread with the
  daemon's own runtime handle (`Handle::block_on` inside `spawn_blocking`,
  `domain::isolate::run_isolated`), never a runtime of their own (#107), so they
  don't poison the `#[async_trait]` future. Used by the contacts and groups
  queries.
- Prometheus is exposed via `AdminService.GetMetrics` (no second/TCP listener);
  `AdminService.Check` reports daemon liveness + readiness (the storage engine
  answers a ping) and the store's `blob_format` (#84).
- **Reconnection is never the core's job.** The library reconnects transient drops
  with backoff; the edge owns any reconnect after a terminal exit (401/409/logout).
  The core only emits truthful connection state + a clean terminal signal.

## Verification
- `scripts/ci.sh` runs every gate; see
  [CONTRIBUTING.md](../CONTRIBUTING.md#getting-the-gates-green).
- Tests live next to the code (unit, `*_tests.rs` siblings), in
  `crates/wamux/tests/` (service suites over a real socket, storage suites against
  each engine) and in `crates/wamux-tools/tests/`. `scripts/ci.sh` runs them; the
  `#[ignore]` scale tests only with `scripts/ci.sh --full`.
- Manual (needs a phone): `grpcurl -unix -plaintext /run/wamux.sock list`;
  CreateAccount → PairWithQr/PairWithCode → send/receive text+media →
  groups/contacts; restart, call ConnectAccount, and confirm the session resumes
  without re-pairing.
