# Upgrading from 0.1 to 0.2

From 0.1.0 to 0.2.0. The `wamux.v1` package keeps its name and breaks, as the
CHANGELOG allows while the version is `0.x`. Everything here shipped in 0.2.0;
read the later guides in [the index](README.md) if you go further.

Build the edge against the released 0.2 `.proto` files, not against `main`.

## Order of operations

1. Stop the 0.1 daemon and back up the store (the database, or the SQLite file
   with its `-wal` and `-shm`).
2. Migrate the store to the 0.2 format ([The store](#the-store)).
3. Fix the deployment: socket, spool, unit ([Operators](#operators)).
4. Regenerate the edge's client and port it ([Edge authors](#edge-authors)).
5. Start 0.2, then check `AdminService/Check` answers `BLOB_FORMAT_PROTOBUF`.

## Operators

### The store

A 0.1.0 store holds whatsapp-rust 0.6 blobs in positional bincode, which 0.2
cannot read until two one-shot migrations rewrite them. The binaries that do it
exist only at commit `ac4c21b`. With the daemon stopped and a backup taken:

```sh
git checkout ac4c21b
cargo run --release --features migrate-0-7 --bin migrate_0_7               # dry run
cargo run --release --features migrate-0-7 --bin migrate_0_7 -- --apply
cargo run --release --features migrate-0-7-main --bin migrate_0_7_main     # dry run
cargo run --release --features migrate-0-7-main --bin migrate_0_7_main -- --apply
```

They read the store from `wamux.toml` and the `WAMUX_*` variables (or
`--database-url URL`), refuse to run while a daemon answers on the socket, write
nothing unless every blob converts, and are idempotent.

Then start 0.2. On its first open it converts the store from bincode to
protobuf in one transaction, checking every row before writing, and stops with
nothing changed if one row will not convert, naming it. Nothing to run. After
it, each account's first connect does one full Noise handshake.

0.2.x is the last release line that converts a bincode store; 0.3 refuses one.
Upgrade through 0.2 before 0.3, and confirm with
`grpcurl -unix -plaintext /run/wamux.sock wamux.v1.AdminService/Check`, which
must report `"blobFormat": "BLOB_FORMAT_PROTOBUF"`.

Also new for the store:

- A new `sqlite://` or `turso://` file is created `0600`. An existing file that
  group or others can read is reported with a `WARN`: run the `chmod 600` it
  names. The daemon does not change it for you.
- SQLite now runs at `synchronous = FULL` with a writer and a read pool, so an
  in-memory DSN (`:memory:`, `mode=memory`) is refused at startup.
- `store_key_file` (optional) encrypts the store's secrets at rest. See
  `docs/DEPLOYMENT.md`, "Encryption at rest", before turning it on.

### The socket (#77)

No `.proto` change, but a deployment that worked on 0.1 can fail to start.

- **A live socket at `socket_path` stops startup** (`another wamux is serving
  <path>`); something that is not a socket is refused and left alone. Only a
  socket that refuses connections (a stale file) is replaced. Stop the old
  daemon before starting the new one; `systemctl restart` already does.
- **`socket_group` now `chown`s the socket**, by name or numeric gid, and
  startup fails if the group does not exist or the daemon's user is not in it
  (root may use any group). Add the user to the group, or remove the key.
- A parent directory the daemon creates is `0750`; an existing one keeps its
  mode. The socket is bound in a private `0700` sibling and renamed into place,
  so it never appears wider than `socket_mode`.
- New, optional: `allowed_uids` and `allowed_gids`. With either set, only those
  `SO_PEERCRED` peers are served; the rest get `PermissionDenied("peer not
  allowed")`, reflection included. There is no implicit uid, not even the
  daemon's. Only the effective gid is visible: list the uid of a peer that is in
  a group only as a supplementary one.

### The media spool (#79)

Media is staged on disk instead of in memory.

- **`media_spool_dir` must exist or be creatable, and be writable**, or startup
  fails naming the path. Default `/var/cache/wamux` (env
  `WAMUX_MEDIA_SPOOL_DIR`). A unit written by hand needs `CacheDirectory=wamux`
  and `Environment=WAMUX_MEDIA_SPOOL_DIR=%C/wamux`, as `contrib/wamux.service`
  now has (under `ProtectSystem=strict` the directory must be one systemd makes
  writable). Never a tmpfs or `/tmp`: that is RAM. See `docs/DEPLOYMENT.md`.
- **DownloadMedia refuses a file above `media_max_bytes`** with
  `ResourceExhausted("media exceeds size limit")` before fetching (a descriptor
  with `file_length = 0` is capped while written). Raise `media_max_bytes` if
  you download larger files.
- New: `media_spool_max_bytes` (default 2 GiB, `0` = unlimited) bounds all
  transfers in flight together. Past it a transfer gets
  `ResourceExhausted("media spool budget exhausted")`. Retrying is the edge's
  call.
- SendMedia and PostStatusMedia validate the media type from the header before
  reading any byte, so a stream with a bad type and a later error now reports
  the type.

### Bounded defaults (#80)

- **`replay_max_event_bytes` defaults to 262144 (256 KiB)**, was `0` (no cap).
  A larger event is delivered live but not kept for `replay_from_ring`. Set it
  higher, or to `0` for the old behavior, only if you replay events above 256
  KiB (none was seen outside history sync, which the ring never kept).
- **The `method` label of `wamux_grpc_requests_total` and
  `wamux_grpc_request_duration_seconds` is `unknown`** for a path the daemon
  does not serve (`grpc.reflection.v1alpha` included). A dashboard that
  selected an invalid path selects `method="unknown"`.

### The systemd unit (#188)

Copy the new `contrib/wamux.service`, then `systemctl daemon-reload` and
restart. It adds `StateDirectoryMode=0700` (systemd tightens an existing `0755`
state directory on start) and the spool settings above.

## Edge authors

Regenerate the client from the 0.2 `.proto` files. A field whose type changed
took a new number and `reserved` the old one, so an edge that was not rebuilt
is never misread: it reads the retyped event fields as empty, and its requests
answer `InvalidArgument("missing jid")`. Nothing below works until it is
rebuilt.

### MarkRead sends a receipt (#20)

Same signature, different effect. `MarkRead` used to mark the chat read on the
account's own devices and send nothing; it now sends the read receipt that turns
the sender's ticks blue, reading `message_ids` and (in a group) `sender`.

- Called it to send a receipt: nothing to do; fill `message_ids` and `sender`.
- Called it for the effect on your own devices: call the new `MarkChatRead`
  (same request; reads only `account` and `chat`).
- Want both, as the official app does: call both. The core does not compose
  them.

An empty `message_ids` sends nothing and is not an error. An unset or empty
`sender` means absent (a DM). No confirmation comes back: verify on a second
device, not from the call returning.

### GetPushName takes an AccountRef (#1)

`ContactService.GetPushName` takes an `AccountRef` instead of a `JidRequest`. It
always answered the account's own push name and ignored the jid. Send the
`AccountRef` you put in `JidRequest.account`. A peer's push name arrives on the
events that carry it (`InboundMessage.push_name`).

### PresenceUpdate.online is optional (#24)

`online` is `optional bool`, set only on real presence and unset on a chat state
(it was a hard-coded `true`). Light an "online" dot from presence events only.
`PresenceUpdate.chat` is new: the conversation a chat state happened in (the
group in a group).

### Every jid is the `Jid` message (#72)

Every field that carried a jid as a `string` is `Jid`. The rules:

- The field takes a new number; only the `_jid` suffix of a name is dropped
  (`remote_jid` is `chat`, `group_jid` is `group`).
- A required jid that is unset or has an empty `value` answers
  `InvalidArgument("missing jid")` (several answered `"empty jid"`); a malformed
  one `invalid jid '<value>': <reason>`. Each entry of a repeated field
  (`participants`, `jids`) is required.
- An optional one (a DM's `participant`) may be unset or `Jid { value: "" }`.
- A jid the core answers with is relayed verbatim, and an absent one is an unset
  field, never an empty string: check presence, not `""`.

### Enums instead of strings (#73)

Enum-like values are proto enums. `*_UNSPECIFIED = 0` means no value;
`*_UNKNOWN = 1` is a value wamux does not name, with the original in a `*_raw`
(token) or `*_code` (number) field next to it, set only on `UNKNOWN`. Each
field took a new number. Compare enum names, never numbers.

| Message | Before | After |
|---|---|---|
| `ReceiptEvent` | `string type = 4` | `ReceiptType type = 8`, `string type_raw = 9` |
| `PresenceUpdate` | `string chat_state = 4` | `ChatState chat_state = 8` |
| `CallEvent` | `string action = 3` | replaced by the typed call event below |
| `AppStateUpdate` | `string kind = 2` | replaced by the typed app-state update below |

| `ConnectionStateChanged` | `string detail = 2` (`Debug`) | `LoggedOutInfo logged_out = 3`, `TemporaryBanInfo ban = 4` |

- `ReceiptEvent.type`: each token maps to `RECEIPT_TYPE_<TOKEN>` (`read-self`
  is `READ_SELF`, `hist_sync` is `HISTORY_SYNC`), plus `SENT`. Any other token

### Typed messages instead of JSON (#74)

Every JSON payload inside a `bytes` field is a protobuf message, except
`RawEvent.payload`. Read the message instead of parsing JSON. In each one an
absent value is unset (never `0` or `""`), times are milliseconds (a value of
unverified unit crosses as sent, and its comment says so), and every jid is a
`Jid` (no more `{"user":..,"server":..}` objects).

| Message | Before | After |
|---|---|---|
| `GroupJidResponse` | `bytes metadata = 2` | `GroupMetadata metadata = 4` (unset after JoinWithInvite) |
| `GroupMetadataResponse` | `bytes metadata = 1` | `GroupMetadata metadata = 2` |
| `GroupSummary` | `bytes metadata = 4` | `GroupMetadata metadata = 6` |
| `MembershipRequestsResponse` | `bytes requests = 1` | `repeated MembershipRequest requests = 2` |
| `BusinessProfileResponse` | `bytes raw = 1` | `BusinessProfile profile = 2` (unset: no profile) |
| `GroupUpdate` | `kind = 2`, `bytes raw = 3` | header fields and `oneof action` |
| `ContactUpdate` | `kind = 2`, `bytes raw = 3` | `timestamp`, `action_timestamp`, `from_full_sync`, `action` |
| `AppStateUpdate` | `kind`, `bytes raw = 3` | `timestamp`, `action_timestamp`, `from_full_sync`, `oneof action` |
| `CallEvent` | `action`, `action_raw`, `bytes raw = 4` | the stanza's fields and `oneof action` |

**Group metadata** (`group_metadata.proto`) carries every field the library
parses, not the five the JSON had. `subject` is unset when absent (it was `""`;
`GroupSummary.subject` keeps `""`). Each participant is whole: `jid`,
`phone_number` (unset when absent), `lid`, `username`, `type` (`member`,
`admin`, `superadmin` as `GROUP_PARTICIPANT_TYPE_*`) and `details`. Creation,
subject, description, join and request times are now ms (they were seconds).
A membership request's jid is `.jid.value` and its `request_time` is ms.

**Business profile**: same names as the JSON keys. `day_of_week` and `mode` are
enums with `*_raw` on `UNKNOWN`; `open_time`/`close_time` are minutes past
local midnight.

**Group updates** (`group_update.proto`): switch on the `oneof action` case
where you read `action.type`; the case has the tag's name (`add`, `remove`,
`promote`, `subject`, `create`, ...), and an action the library does not name
arrives as `unknown` with its tag. `timestamp` was RFC 3339 and is ms.
`create` carries the new group's `GroupMetadata`. A participant's `participant`
role is `GROUP_PARTICIPANT_TYPE_MEMBER`.

**Contact updates**: `action.lid_jid`/`pn_jid` are `action.lid`/`pn`;
`timestamp` and `action_timestamp` are ms (`action_timestamp` unset when the
mutation had none).

**App-state updates** (`app_state.proto`): the old `kind` values are the
`oneof action` cases `archive`, `pin`, `mute`, `star`, `mark_read` (false means
unread) and `delete_chat`. The star's chat, participant and id moved into
`star`. A message range's times were seconds and are ms, and its keys are
`MessageKey`s.

**Call events** (`call.proto`): the old action values are the `oneof action`
cases of the same name (`RELAY_LATENCY` is `relay_latency`, `VIDEO_STATE` is
`video_state`, `RAISE_HAND` is `raise_hand`); an action added later is
`unknown_action` with its tag. `call_creator` and `stanza_id` are top-level for
every action; `timestamp` was seconds and is ms. `terminate`'s durations cross
as sent (unit not verified).

**Logout and ban stanza** (#138, additive): `LoggedOutInfo.stanza` and
`TemporaryBanInfo.stanza` carry the server's `<failure>` or `<stream:error>` as
a `StanzaNode` (unset for a local logout). An account lock's `appeal_token`,
`violation_reason` and `vt` are only there; the core does not parse them.

**Group create, link, unlink, sub-group suggestions** (#146, additive):
`GroupCreated.stanza`, `GroupLinked.stanza`, `GroupUnlinked.stanza` and the two
sub-group suggestion cases carry the raw element as a `StanzaNode`. Its
`content` may be `text` or `bytes`: read both.

### Pairing streams end on their own (#150)

PairWithQr and PairWithCode now also deliver `code_refresh`, `code_error` and
`qr_codes_exhausted`, and the stream ends after `code_error`, `code_refresh`, or
`qr_codes_exhausted` with `disconnected` true, as well as after `paired` and
`error`. Read the stream until it ends instead of waiting for `paired` or
`error` alone. Asking again is the edge's decision.

### New refusals

Requests that could never succeed answered `Unavailable` ("core down") or
reached the server. They now fail fast, with a status that says the request is
wrong, so retrying them cannot help.

| RPC | Request | Now |
|---|---|---|
| Every GroupService RPC with a `group` (#96) | a valid jid not on `@g.us` | `InvalidArgument`, nothing sent |
| `JoinWithInvite`, `PreviewInvite` (#96) | empty or unreadable code | `InvalidArgument("invalid or empty invite code")` |
| `CreateGroup` (#96) | a `@lid` participant with no known phone number | `FailedPrecondition`: send the phone jid, or wait for the mapping |
| `SetGroupDescription` (#96) | changed by another device first | still `Unavailable`, now with `wa-code=409` |
| `GetNewsletterMetadata`, `GetNewsletterMessages` (#99) | a jid not on `@newsletter` | `InvalidArgument`, at once (history used to hang 75 s) |
| `SendPoll` (#101) | fewer than 2 or more than 12 options, `selectable_count` 0 or above the count, duplicates | `InvalidArgument("invalid poll: ...")` |
| `MuteChat` (#101) | a deadline in the past (any invalid app-state request) | `InvalidArgument` |
| `PostStatusText`, `PostStatusMedia` (#101) | no `recipients` | `InvalidArgument`, before any upload |
| `DeleteMessage` (#41) | `for_everyone` on a `status@broadcast` key | `InvalidArgument` naming `RevokeStatus` |
| SendReaction, EditMessage, DeleteMessage, StarMessage (#115) | an empty target message id | `InvalidArgument("empty message id")` |
| Any send with a quote (#115) | a quote key with an empty id | `InvalidArgument` |
| Any send (#115) | a malformed mention or participant (used to relay unparsed) | `InvalidArgument` |

`selectable_count` is proto3's default 0: set it. `JoinWithInvite` now sets
`GroupJidResponse.join_outcome` (`JOINED` or `PENDING_APPROVAL`), the only way
to tell a join from a request waiting for an admin.

### Smaller changes

- A `@c.us` jid in a request is parsed as `@s.whatsapp.net` (the library's
  parse), so the echo and every answer name it that way.
- Media downloads verify the hashes the message declares: a file whose hash
  does not match fails.
- `GetNewsletterMetadata` for a channel that does not exist answers `NotFound`
  (`newsletter <jid> not found`); a MEX error carries `wa-code`/`wa-text`, and
  `405` maps to `PermissionDenied`.
- A channel history answer without `<messages>` is `Unavailable` (it was an
  empty page).
- A `wa-text` trailer whose text is not ASCII is left out (the code still rides
  `wa-code`). `account <uuid> not found` names the uuid in lowercase.
- A status recipient given by phone number whose LID the client does not know
  is still dropped silently by the library: send LIDs when posting a status.
- The six library-built sends (poll, vote, edit, revoke, status text and media)
  now echo a from-me `InboundMessage` like the other sends, so every
  subscriber sees them.
